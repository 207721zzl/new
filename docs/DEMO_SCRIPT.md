# EvidenceRAG 3～5 分钟当前演示脚本

> 演示前执行 `docker compose ps`，确认 API、MySQL、Milvus、etcd 和 MinIO 为 `healthy`。公网演示还要实际打开 tunnel 日志中的最新地址，不能只看容器是否为 `Up`。

## 0:00–0:40 项目定位

打开 `http://127.0.0.1:8000/`。说明这是独立企业文档 RAG，而不是通用聊天机器人：当前在线入口只做文档上传、解析、检索、证据回答、引用和反馈，不执行旧 Text2SQL、经营归因、销量预测或 MCP。

调用 `/api/v1/health/ready`，展示 DeepSeek、Milvus、MySQL 和本地模型状态，以及当前动态的知识片段数量。

## 0:40–1:30 Docker 与本地模型

展示 `docker compose ps`：

- API 使用 PyTorch CUDA 容器并加载 NVIDIA GPU；
- BGE-M3 和 `bge-reranker-v2-m3` 从宿主机只读挂载；
- MySQL 保存文档、父块、任务、会话和反馈；
- Milvus、etcd、MinIO 保存可重建检索索引；
- 本机 API 只绑定 `127.0.0.1:8000`。

如果展示公网入口，从 `docker compose logs tunnel` 读取当前随机地址，并说明它是无认证的临时演示通道，重启后会变化。

## 1:30–2:20 多格式增量导入

选择少量具有代表性的 PDF、Word 或 Excel，保持 `recreate=false`。说明：

1. 文件先校验并落盘；
2. MySQL 创建批次和任务；
3. API 后台按文件顺序解析；
4. 父块写入 MySQL，子块经 BGE-M3 写入 Milvus；
5. 页面轮询批次状态并展示成功、失败和切块数量。

当前入库实现面向单机试点，同批次顺序处理；不要把它描述为分布式并行管道。

## 2:20–3:00 父子切块与混合检索

说明父块按章节、页面、表格或工作表组织，默认目标约 1,600 字符；子块在父块内按约 400/80 切分。

提问后展示：

`多轮问题补全 → Dense + BM25 → RRF → bge-reranker-v2-m3 → 证据阈值 → 父块恢复`

强调子块负责准确召回，父块负责完整上下文；RRF 分数不是概率，最终排序主要看 Reranker。

## 3:00–3:50 回答、引用与连续追问

提出一个资料中明确可回答的问题，再追问“那它的分母呢？”之类依赖上下文的问题。展示：

- 独立问题补全和检索改写；
- 答案中的引用编号；
- 文档标题、来源、版本、章节或页码；
- 刷新页面后仍可通过运行记录和会话读取结果。

公网 Quick Tunnel 不支持 SSE 时，页面会自动退回轮询，不影响最终答案展示。

## 3:50–4:20 安全拒答

提出一个知识库完全没有的问题。系统在证据阈值处返回“现有知识库资料不足”，不调用最终生成模型编造内容。

## 4:20–5:00 工程化边界

打开 `/docs` 展示上传、批次状态、文档列表、纯检索、同步回答、异步运行、会话和反馈接口。

最后明确当前边界：

- 适合本机少量文档试点；
- 扫描 PDF 质量取决于 OCR 配置和原件；
- 大批量入库尚未使用独立任务队列、断点续跑、Bulk Import 或蓝绿 Collection；
- 生产化前需要真实文档盲测、权限隔离、固定域名和合规配置。
