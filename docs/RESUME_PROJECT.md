# EvidenceRAG 面试说明

## 简历项目描述

**EvidenceRAG｜多格式企业文档知识问答｜Python / FastAPI / DeepSeek / BGE-M3 / BGE Reranker / Milvus / MySQL / Docker GPU**

- 将原经营分析 Agent 收敛为独立 RAG 系统，打通 PDF、DOCX、Markdown、HTML、TXT、Excel、JSON 的上传、解析、索引、检索、回答、引用和反馈闭环。
- 设计格式无关的 `KnowledgeDocument + SourceBlock` 契约，保留章节路径、页码、表格行号、文件哈希和版本；使用稳定 SHA-256 ID 支持幂等重建。
- 实现结构感知父子切块：章节/页面/工作表优先组成父块，父块内创建重叠子块；子块参与 BGE-M3 Dense + Milvus BM25 + RRF + BGE Reranker，命中后从 MySQL 恢复父块生成。
- 增加多轮独立问题补全、检索查询改写、重排阈值、同父块去重、知识不足拒答和文档/章节/页码引用，降低无证据生成。
- 使用 FastAPI、异步后台任务、SSE 与轮询回退、MySQL 状态持久化、Alembic、Docker Compose、pytest 和 Ruff 完成可运行工程化闭环。
- 将 API 部署在 PyTorch CUDA 容器中，通过只读卷加载宿主机 BGE-M3 和 `bge-reranker-v2-m3`，并用 Cloudflare Quick Tunnel 提供无需路由器端口映射的临时演示入口。

## 当前实际部署

- 默认运行服务：`api`、`mysql`、`standalone`、`etcd`、`minio`、`tunnel`。
- 本地页面固定绑定 `127.0.0.1:8000`；公网地址由 Quick Tunnel 动态产生，重启后变化。
- 模型在启动时预加载到 NVIDIA GPU；模型目录不打包进镜像。
- 当前公网入口按试点要求未增加账号认证，不作为生产安全方案。
- 当前批量索引由 FastAPI `BackgroundTasks` 在 API 进程内执行，同批次文件顺序处理，适合本机少量文档试点。

## 面试官常见追问

### 为什么不用一个固定大小直接切块？

固定小块召回准但语义碎，固定大块语义完整但向量主题容易被稀释。我用子块召回、父块生成：先按标题、页面或表格组织父块，再在父块内部切 400 字符左右的重叠子块。命中子块后通过 `parent_chunk_id` 回查父块，这样把检索粒度和生成粒度解耦。

### 父块到底按照什么切？

结构边界优先、长度约束其次。Markdown/Word/HTML 看标题路径，PDF 不跨明确页面，Excel 看工作表和行窗口；父块目标约 1,600 字符，允许到 1.25 倍。只有单个段落或表格本身过大时才按句末窗口拆分。

### 怎么保证语义完整性？

不是只靠 overlap。我有七层保护：解析保结构、父块按结构、子块不跨父块、句末优先、Embedding 拼标题章节、命中后恢复父块、证据不足拒答。引用继续携带章节和页码，最终还能人工核验。

### 为什么 Dense 和 BM25 都要？

Dense 擅长语义相似和同义表达，BM25 擅长型号、专有名词、缩写和精确词。两路候选用 RRF 融合，避免直接比较不可比的原始分数，然后让交叉编码器基于“问题—候选”联合编码做精排。

### MySQL 和 Milvus 为什么都要？

Milvus 负责高效召回，可随时从真源重建；MySQL 保存原文、完整父块、版本、状态、会话和任务。生成阶段回 MySQL 取父块，可以避免向量库字段长度和一致性问题。索引只有在两边都成功后才标 `completed`。

### 文档解析准确率是多少？

我不会报一个没有口径的统一百分比。电子 DOCX/TXT 和文本型 PDF 通常是确定性提取，扫描 PDF 受清晰度、旋转、语言和 OCR 影响，复杂表格又是另一种问题。实际要分别测 CER/WER、标题层级 F1、单元格准确率、顺序和页码定位，再测端到端检索 Recall@K 与引用准确率。当前回归只能说明功能没有退化，不能当泛化准确率。

### 如何减少幻觉？

召回后用 Reranker 和最低阈值做证据门控；同父块去重；Prompt 明确只允许使用给定证据；没有命中直接返回知识不足；答案返回来源、版本、章节、页码和分数。进一步可增加引用蕴含校验和基于 NLI 的生成后验证。

### 文档更新或重复上传怎么办？

文件有 SHA-256，文档、父块、子块 ID 由文档 ID、版本、位置和内容稳定生成。当前增量索引会按文档删除旧向量并写入新块，重复内容保持稳定 ID。MySQL 和 Milvus 仍是应用层最终一致；生产环境需要增加 outbox、补偿任务或蓝绿 Collection，避免更新中途失败形成短暂空窗。

### 这个项目还有哪些不足？

扫描 PDF OCR 默认关闭，复杂版面和合并单元格仍需要更强的版面模型；尚未用独立企业语料完成分层盲测；批量索引还是 API 进程内顺序任务，不具备持久队列和断点续跑；Milvus 与 MySQL 是应用层最终一致，而非分布式事务；公网 Quick Tunnel 没有固定域名、SLA 或认证；生成后引用蕴含校验、权限过滤和租户隔离还可以继续补。主动说清这些边界比给出不可信的高准确率更专业。
